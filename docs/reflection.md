# SQL 강의 회고 — 느낀 점과 개선 계획

> **가장 큰 변화:** SQL을 ‘답을 출력하는 문법’으로만 보지 않고, **답의 기준을 직접 정하고 검증하는 도구**로 생각하게 됐다.

## 1. 처음에는 숫자가 나오면 끝이라고 생각하기 쉬웠다

청구 기록을 조건에 맞게 조회하고 개수를 구할 때, 결과가 0건이면 단순히 데이터가 없다고 해석하기 쉬웠다. 그런데 강의의 `I10`과 `I109` 사례처럼, **찾으려는 질병의 표현과 실제 저장 코드가 다르면 SQL이 정상 실행돼도 원하는 기록을 놓칠 수 있다.**

이후에는 쿼리보다 먼저 데이터의 값과 형태를 확인해야 한다는 생각이 들었다. `SELECT DISTINCT`, 코드 마스터, 기간·서식 조건을 미리 살펴보는 습관이 필요하다.

**다음에 바꿀 행동:** 조건을 적자마자 집계하지 않고, 먼저 관련 코드값이 어떤 형태로 저장됐는지 작은 조회로 확인한다.

## 2. 결과의 단위가 달라지면 같은 데이터도 다른 질문이 된다

J209 관련 과제에서 **2,554건**의 명세서와 **894명**의 수진자를 구분한 부분이 기억에 남는다. 둘 다 틀리지 않은 숫자지만 하나는 **기록 수**, 하나는 **고유 인원**이다. 이 구분 없이 숫자만 보여 주면 다른 사람이 환자 수를 잘못 이해할 수 있다.

이 부분에서 `GROUP BY`와 윈도우 함수의 차이도 연결해서 이해하게 됐다. `GROUP BY`는 묶어 요약하고, `LAG`나 `ROW_NUMBER`는 방문별 기록을 유지하면서 순서와 이전 값을 더한다. 무엇을 보고 싶은지에 따라 쿼리의 형태부터 달라진다.

**다음에 바꿀 행동:** 결과 열에 `claim_count`, `patient_count`, `gap_days`처럼 단위를 드러내고, 집계 건수와 고유 ID 수를 따로 검산한다.

## 3. JOIN을 배운 뒤에는 결과에서 사라진 사람이 보이기 시작했다

사망 기록을 코호트에 연결하는 강의에서는 `INNER JOIN`에 따라 **처음 선정한 분석 대상 자체가 줄어드는 상황**을 다뤘다. 문법상 정상인 JOIN이더라도, 사망 기록이 없는 사람을 빼면 사망 기록 비율의 분모가 달라진다. 반대로 `LEFT JOIN`을 쓴다고 무조건 안전한 것도 아니다. 상대 테이블에 동일한 환자의 행이 여러 개라면 수가 늘어날 수 있다.

결국 JOIN은 단순히 표를 옆으로 붙이는 것이 아니라, **분석에 남는 사람이 누구인지 정하는 작업**이라는 생각이 남았다.

**다음에 바꿀 행동:** 코호트를 먼저 CTE로 고정하고, 연결 직전·직후 `COUNT(*)`와 `COUNT(DISTINCT pt_sbst_no)`를 확인한다. 값이 달라졌다면 사라진 ID와 중복된 ID를 조사한다.

## 4. 기록의 부재를 사실의 부재로 해석하면 안 된다

과제에서는 진단일부터 **1,095일 이내 사망 기록**을 분류했다. 그런데 그 기간 동안 환자에게 무슨 일이 있었는지 끝까지 관찰한 자료가 없다면, **사망 기록이 없다는 것만으로 그 사람이 3년 동안 생존했다고 확정할 수는 없다.**

이것이 중도절단, 즉 **관찰 기간이 끝나기 전에 기록이 끊기는 문제**를 배워야 하는 이유라고 이해했다. SQL로 사건을 0/1로 계산하는 방법과, 그 숫자가 무엇을 증명하는지는 구분해야 한다.

**다음에 바꿀 행동:** 분석 결과의 이름부터 정확하게 적는다. 이번 자료는 실제 생존율이 아니라 **교육용 데이터의 사망 기록 집계**라고 설명한다. 관찰 기간과 누락 가능성도 함께 남긴다.

## 5. AI와 협업할수록 검증하는 능력의 가치가 커진다

AI를 활용하면 SQL 초안을 빠르게 만들 수 있지만, 그 쿼리가 **정확히 어떤 대상을 선택했는지**는 사용자가 확인해야 한다. 조회 기간이 다르거나, 조인 키가 충분하지 않거나, 집계 단위가 바뀌어도 문법 오류 없이 결과가 나올 수 있기 때문이다.

따라서 앞으로는 AI가 완성한 코드라도 **내가 설명하지 못하는 구문은 그냥 통과시키지 않는 것**을 원칙으로 삼고 싶다. 쿼리를 직접 이해하는 일이 AI를 더 유용하게 쓰는 방법이라고 느꼈다.

**다음에 바꿀 행동:** AI가 작성한 SQL을 `SELECT` 결과 열 → `WHERE` 조건 → `JOIN` 키 → 집계 기준 → `NULL` 처리 순서로 검토한다. 결과만 저장하지 않고 수정 이유까지 함께 적는다.

## 앞으로의 작업 체크리스트

- [ ] 문제의 대상·기간·지표를 한 문장으로 정리했다.
- [ ] 한 행이 무엇을 의미하는지 확인했다.
- [ ] 조회 조건에 쓰인 실제 코드값과 자료형을 살펴봤다.
- [ ] JOIN 전후 전체 행과 고유 ID를 비교했다.
- [ ] 결과에 `건/명/일/%` 단위와 분모를 표시했다.
- [ ] 기록의 부재와 실제 사건의 부재를 구분했다.
- [ ] 원본 쿼리·수정 이유·결과를 다음 복습용으로 보관했다.
