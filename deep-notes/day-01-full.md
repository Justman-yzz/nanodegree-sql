## 1일차 핵심 한눈에

AI가 쿼리를 써 주는 시대에도 결과가 맞는지 판단하는 일은 사람 몫이고, 그 판단은 SQL이 데이터를 어떻게 바꾸는지 아는 데서 나옵니다.

### 개념 핵심

| # | 핵심 |
| --- | --- |
| 1 | 테이블은 시트, 행은 한 건, 열은 항목. 명세서 한 행은 진료 한 건의 청구 |
| 2 | 실행 순서는 FROM → JOIN → WHERE → SELECT → ORDER BY → LIMIT (쓰는 순서와 다름) |
| 3 | WHERE는 행을 줄이고, SELECT는 열을 줄인다 |
| 4 | AND는 행이 줄고, OR는 행이 늘어난다. 문자와 날짜는 작은따옴표 |
| 5 | ORDER BY와 LIMIT은 쿼리 맨 끝. ORDER BY 없는 LIMIT은 어떤 행이 나올지 정해져 있지 않다 |
| 6 | 명세서에는 코드만 있고 이름은 마스터 테이블에 있다. JOIN은 같은 코드끼리 옆으로 붙여 열을 늘린다 |
| 7 | JOIN 뒤에는 `c.`, `s.` 별칭을 붙이고, ON을 빼먹으면 행이 서로 곱해진다 |
| 8 | 0행이면 쿼리를 의심하기 전에 값이 실제로 어떻게 들어 있는지부터 본다 (I10 vs I109) |
| 9 | 결과는 항상 행 수, 첫 행, 열 이름으로 스스로 검증한다 |

### 철학 핵심

| # | 핵심 |
| --- | --- |
| 1 | 쿼리는 에이전트가 쓰고, 맞는지 판단하는 일은 사람 몫 |

| 3 | 직무의 공통분모는 SQL, R/Python 같은 통계 도구, 청구/EMR 데이터 |

## 2교시 A: 명세서 데이터 이해

명세서는 병원이 진료비를 심평원에 청구할 때 내는 서류이고, `claim` 테이블의 한 행이 명세서 한 건입니다. `kr_claims`는 그 청구 자료의 모양을 본뜬 실습용 DB입니다.

| 항목 | 내용 |
| --- | --- |
| 일시 | 2026-10-06(화) 11:00\~11:50 |
| 사용 테이블 | `claim`, `sick_master`, `hospital_open` |
| 목표 | 조건에 맞는 행을 골라 정렬하고, 상병마스터를 JOIN해 상병 한글명을 붙인다 |
| 풀려는 문제 | 2025년 12월 외래 청구 중 금액이 큰 건은 무슨 병이었나 |
| SQL 패턴 | SELECT, WHERE, ORDER BY, LIMIT, JOIN |
| 시간 | 이론 20분, 실습 30분, 풀이 5분 |

### 테이블 지도

| 테이블 | 한 행의 의미 | 행 수 | 잇는 열 |
| --- | --- | --- | --- |
| `claim` | 명세서 한 건 (진료 한 번의 청구) | 38,375 | `jid`, `yid`, `main_sick` |
| `patient` | 수진자 한 명 | 3,000 | `jid` |
| `institution` | 요양기관 한 곳 (이름 없음) | 2,184 | `yid`, `cl_cd` |
| `sick_master` | 상병코드 한 개 | 21,299 | `sickcd` |
| `code_table` | 코드 한 개와 그 이름 | 215 | `code_type`, `code` |
| `hospital_open` | 실제 요양기관 한 곳 (병원급 이상) | 4,215 | 없음 (명세서와 이어지지 않음) |

- 가상 기록: `patient`, `claim`, `institution`은 지어낸 데이터입니다. 열 이름은 심평원 환자표본자료 구조를 따랐고, 환자 비율과 진료비 수준은 공식 통계에 맞췄습니다.
- 실제 자료: `sick_master`, `code_table`, `hospital_open`은 심평원이 공공데이터포털에 공개한 자료입니다.
- 기간은 2024-01-01부터 2025-12-31까지 2년입니다.
- `code_table`은 여러 종류의 코드가 한 테이블에 있어서 `code_type`과 `code` 두 열을 함께 써야 이어집니다(3교시).
- 열 설명은 `SHOW FULL COLUMNS FROM claim;`을 실행하면 `Comment` 칸에 나옵니다.

## 2교시 B: SELECT, WHERE, ORDER BY, LIMIT

SQL은 쓰는 순서와 실행 순서가 다르고, 각 단계는 행을 줄이거나(WHERE) 열을 줄이거나(SELECT) 순서를 바꾸거나(ORDER BY) 자릅니다(LIMIT). 이 순서를 알아야 에러와 이상한 결과를 읽을 수 있습니다.

### SELECT의 틀과 실행 순서

```sql
SELECT mid, recu_fr_dd, main_sick
FROM claim
WHERE fom_tp_cd = '031'
ORDER BY rvd_rpe_tamt_amt DESC
LIMIT 10;
```

| 구분 | 순서 |
| --- | --- |
| 쓰는 순서 | SELECT → FROM → WHERE → ORDER BY → LIMIT |
| 실행 순서 | FROM → (JOIN) → WHERE → SELECT → ORDER BY → LIMIT |

| 단계 | 하는 일 | 데이터 변화 |
| --- | --- | --- |
| FROM | 테이블을 통째로 가져옴 | 38,375행, 모든 열 |
| WHERE | 조건에 안 맞는 행을 버림 | 행이 줄어듦 |
| SELECT | 필요한 열만 남김 | 열이 줄어듦 |
| ORDER BY | 순서를 바꿈 | 행 수는 그대로 |
| LIMIT | 위에서 N행만 자름 | 행이 더 줄어듦 |

SELECT에서 붙인 별명(`AS`)은 WHERE보다 나중에 생기므로 WHERE에서는 쓸 수 없고, ORDER BY에서는 쓸 수 있습니다.

### WHERE: 조건으로 행 고르기

```sql
SELECT COUNT(*) FROM claim WHERE fom_tp_cd = '031';
SELECT COUNT(*) FROM claim WHERE recu_fr_dd BETWEEN '2025-12-01' AND '2025-12-31';
SELECT COUNT(*) FROM claim WHERE fom_tp_cd = '031' AND recu_fr_dd BETWEEN '2025-12-01' AND '2025-12-31';
```

| 조건 | 뜻 | 남는 행 |
| --- | --- | --- |
| `fom_tp_cd = '031'` | 외래만 | 37,751 |
| `recu_fr_dd BETWEEN '2025-12-01' AND '2025-12-31'` | 2025년 12월 | 1,916 |
| 두 조건을 AND로 | 12월 외래 | 1,913 (12월 입원 3건이 빠짐) |

| 표현 | 뜻 |
| --- | --- |
| `=` | 같다 |
| `BETWEEN a AND b` | a 이상 b 이하 (양 끝 포함) |
| `AND` | 둘 다 맞아야 통과. 조건이 늘수록 행이 줄어듦 |
| `OR` | 하나만 맞아도 통과. 조건이 늘수록 행이 늘어남 |
| `LIKE 'I10%'` | I10으로 시작하는 값 (`%`는 뭐든 이어짐) |

문자와 날짜는 작은따옴표로 감싸고, 숫자는 감싸지 않습니다.

### ORDER BY와 LIMIT: 큰 순서로 10행

```sql
SELECT mid, rvd_rpe_tamt_amt
FROM claim
ORDER BY rvd_rpe_tamt_amt DESC
LIMIT 10;
```

- `DESC`는 큰 값부터, `ASC`는 작은 값부터(기본값)입니다.
- 둘 다 쿼리 맨 끝에 씁니다.
- 전체 1등 진료비는 138,323,000원(명세서 5035264)입니다.
- ORDER BY 없이 LIMIT만 쓰면 어떤 행이 나올지 정해져 있지 않습니다.

## 2교시 C: JOIN으로 코드에 이름 붙이기

명세서에는 상병 코드만 있고 이름은 `sick_master`에 있으므로, 같은 코드를 가진 행끼리 옆으로 붙이는 JOIN으로 이름을 가져옵니다. JOIN 후에도 명세서 행 수는 그대로이고 열만 늘어납니다.

### 개념

`claim.main_sick`과 `sick_master.sickcd`에 같은 값이 있어서 두 테이블이 이어집니다.

- 명세서 5000001의 J304는 상세불명의 알레르기비염
- 명세서 5000004의 L239는 상세불명 원인의 알레르기성 접촉피부염

### 구문의 틀

```sql
SELECT c.mid, c.main_sick, s.krnm
FROM claim c
JOIN sick_master s ON s.sickcd = c.main_sick
LIMIT 5;
```

| 요소 | 뜻 |
| --- | --- |
| `claim c`, `sick_master s` | 테이블 별칭. 긴 이름 대신 짧게 쓰려는 용도 |
| `ON s.sickcd = c.main_sick` | 두 테이블을 잇는 열. 값이 같은 행끼리 짝지음 |
| `c.main_sick` | 열 앞에 별칭을 붙여 어느 테이블의 열인지 표시 |
| `LIMIT 5` | 화면에 5행만 보려는 용도 (안 붙이면 38,375행) |

정렬을 지정하지 않았기 때문에 어떤 5행이 나올지는 정해져 있지 않습니다.

### 내부 동작: 중간 결과 (가상 예시)

`claim`

| mid | main\_sick |
| --- | --- |
| 5000001 | J304 |
| 5000002 | C509 |
| 5000003 | J304 |

`sick_master`

| sickcd | krnm |
| --- | --- |
| J304 | 상세불명의 알레르기비염 |
| C509 | 상세불명의 유방의 악성 신생물 |
| I109 | 기타 및 상세불명의 원발성 고혈압 |

`ON s.sickcd = c.main_sick`으로 짝지은 결과:

| c.mid | c.main\_sick | s.sickcd | s.krnm |
| --- | --- | --- | --- |
| 5000001 | J304 | J304 | 상세불명의 알레르기비염 |
| 5000002 | C509 | C509 | 상세불명의 유방의 악성 신생물 |
| 5000003 | J304 | J304 | 상세불명의 알레르기비염 |

SELECT가 필요한 열만 고르면 최종 결과가 됩니다. `sick_master`의 I109는 짝이 되는 명세서가 없으므로 결과에 나오지 않습니다.

### JOIN이 있을 때의 실행 순서

```
FROM → JOIN → WHERE → SELECT → ORDER BY → LIMIT
```

테이블을 붙인 뒤에 거르고, 고르고, 정렬하고, 자릅니다.

### 자주 하는 실수

| 실수 | 왜 문제인가 |
| --- | --- |
| ON 조건을 빼먹음 | 모든 행이 서로 곱해져서 행이 폭발한다 |
| JOIN 뒤 열 이름에 `c.`, `s.`를 안 붙임 | 두 테이블에 같은 이름의 열이 있으면 어느 쪽인지 몰라 에러가 난다 |
| 날짜에 따옴표를 빼먹음 | `2025-12-01`이 날짜가 아니라 계산식으로 해석된다 |
| ORDER BY 없이 LIMIT | 매번 다른 행이 나올 수 있다 |

## 2교시 D: 라이브 코딩과 실습 1

### 0행의 함정: 고혈압이 0건?

쿼리 문법이 맞아도 결과가 0행일 수 있고, 그 원인은 쿼리가 아니라 값이 들어 있는 모양일 수 있습니다.

```sql
SELECT COUNT(*) FROM claim WHERE main_sick = 'I10';              -- 0 (에러 없음)
SELECT sickcd, krnm FROM sick_master WHERE sickcd LIKE 'I10%';   -- I10, I101, I109
SELECT COUNT(*) FROM claim WHERE main_sick = 'I109';             -- 4403
SELECT COUNT(*) FROM claim WHERE main_sick LIKE 'I10%';          -- 4403
```

| sickcd | krnm |
| --- | --- |
| I10 | 본태성(원발성) 고혈압 |
| I101 | 악성 고혈압 |
| I109 | 기타 및 상세불명의 원발성 고혈압 |

사전에는 `I10`이 있지만 명세서에는 더 세부 코드인 `I109`로 들어 있습니다. 0행이면 쿼리를 의심하기 전에 값이 실제로 어떻게 들어 있는지부터 봅니다. 이 함정은 2일차에 다시 나옵니다.

### 심화

- 심화 1: 결과에 요양기관 종별 이름을 붙입니다. `claim.yid`로 `institution`을, `institution.cl_cd`로 `code_table`의 `종별코드` 행을 잇습니다(테이블 세 개 JOIN은 3교시). 첫 두 행이 `상급종합병원`, 세 번째 행(요통, 696300)이 `의원`이면 맞습니다.
- 심화 2: 수진자 100001의 명세서를 날짜순으로 봅니다(18행). 2024년 11월 알레르기비염(J304) 외래 3번, 2025년 3월부터 유방암(C509) 입원 기록이 이어집니다. 명세서를 사람 단위로 이으면 진료 이력이 되고, 4교시에서 씁니다.

모범답안과 "0행이 나온 이유" 풀이는 수업 후 공개됩니다.
